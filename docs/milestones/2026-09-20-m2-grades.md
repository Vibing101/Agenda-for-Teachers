## What shipped

- **A per-class gradebook.** Unlimited assessment columns, each with a label, a
  type and a percentage weight; a grid of the class's roster against those
  columns; and, per student, the weighted average and the whole-number
  suggestion beside it.
- **All four grade types.** Numeric marks, the descriptive Α–Δ scale, pass/fail
  and free-text comments. The coded ones store a code and print a label, so the
  M9 English pass does not have to touch a teacher's data.
- **The weighting rules, in one pure module** (`src/domain/grades.ts`), with a
  test per branch the spec names: blank columns, weights that do not sum to
  100, the all-zero-weight fallback to a plain average, and the exclusion of
  non-numeric columns from the normalising sum as well as from the marks.
- **The running weight total and its warning**, which appear and disappear as
  the columns are edited and never block a save. A single invalid weight —
  negative, non-numeric, over 100 — is refused at the field, leaving the rest
  of the sheet untouched.
- **Conduct**, as the source's six-level scale plus observations, with the
  conduct sheet's overall result kept as a field the teacher writes and the app
  never computes.
- **The class and year roll-ups**, in the columns the source registry's own
  "Σύνοψη" sheet uses: class average, highest, lowest, at-or-above and below
  the threshold, roster size, and the year-wide "Γενικός μέσος όρος".
- **A per-class pass threshold ("Βάση")**, default 10, with the scale's upper
  bound and the sheet's period caption, in their own table (see "Decisions").
- **PDF export — the first thing this app has ever written to `exports/`.** The
  grade sheet and the conduct sheet each export as a real A4 landscape PDF with
  Greek rendering correctly, through the WebView print-to-PDF path the spec
  resolved on.
- **Schema migration to `user_version = 3`**, added as a forward step; a file
  from the signed-off M0 or M1 build climbs to it rather than being recreated.

## Decisions taken

| Decision | Call taken | Why |
|---|---|---|
| Where the pass threshold lives | A new `class_grading` table keyed by `class_id`, holding `pass_threshold`, `scale_max` and the sheet's `period` caption — not columns on `class` | It is a gradebook setting, and the source registry keeps it in the header of each class's *grade sheet* rather than in the class list. Keeping it out of `class` leaves M1's table, its struct and its round-trip tests untouched, and gives later grading settings somewhere obvious to go. A class with no row reads back as the defaults, so the teacher never meets an empty threshold. **Flagged for the product owner — see "Open questions".** |
| Whether the conduct sheet prints with the grade sheet | Its own button, its own file | The source product keeps "Συμπεριφορά και στάση" as a separate page, and M7 is the only place the spec asks for several pages bundled into one PDF. **Also flagged — see "Open questions".** |
| A row with marks but no weights decided | The average is blank | The spec's formula is "columns that have **both** a value entered **and** a non-blank weight", and its plain-average fallback is defined for weights of *zero*, not for blank ones. So a sheet that has not said how to combine its marks does not get an invented answer; the running total sitting at 0% is the signal. |
| Whether a non-numeric column's weight counts towards the running total | No — the total sums numeric columns only, and the weight field is offered only on a numeric column | The product owner's pre-M2 decision takes such a column's weight out of the average. Showing "Total: 100%" for a sheet that normalises over 70% would then be the opposite of what the warning is for. A weight already stored against a column whose type was changed is still ignored by the calculation, and there is a test for exactly that. |
| What the pass / at-risk counts compare | The rounded suggestion, not the precise average | The source registry's own counts (`COUNTIF` down the `Πρόταση` column) compare the rounded number, and the spreadsheet is the named authority for the summary sheet. |
| What "Γενικός μέσος όρος" averages | The class averages, not every student's average | Same authority: the summary sheet averages its own class-average column, so a class of 30 does not outweigh a class of 8. |
| Decimal separator in printed and displayed numbers | A dot (`17.2`), formatted by the app | Matches the source registry's own display, and keeps a number independent of OS locale for the same reason dates are (the spec's dated-formatting decision). Input accepts a comma as well, because a Greek keyboard offers it first. |
| Pagination of printed sheets | The app measures and lays the document out into A4 blocks; the platform only captures them | Forced by what the two engines do — see "PDF export" below. It gives both platforms the same page structure, the same A4 sheet and the same rows in the same order. It does **not** make the break points identical: row heights come from each platform's own text measurement, and at this gate a 45-row roster came out as five pages on macOS and six on Windows, differing only in whether the closing note shared the last page. |
| A print self-test hook | Two environment variables render a given HTML file to a given PDF and exit | The one thing M2 had to prove — a real PDF with real Greek in it — lives behind a button, and an agent can build and launch the app on either OS but cannot click in it. The document is supplied by the caller, so no Greek string enters the Rust side and the hook exercises the real export path rather than a fixture. It is what produced the Windows evidence below. |
| The sheet header's `Περίοδος` | A free-text caption on `class_grading` | It is a text box in the header of the source's grade sheet. It is **not** the school year's grading periods and not the progress-check periods, which are explicitly out of M2. |

## Open questions for the product owner

**1. Is `class_grading` the right home for the pass threshold?** It is new state
and the spec does not say where it goes. Shipped as its own per-class table for
the reasons in "Decisions taken". The alternative is three more columns on
`class`; if that is preferred it is one migration and one struct, with no change
to the calculation.

**2. Should the conduct sheet print as part of the grade-sheet PDF, or as its
own file?** Shipped as its own, matching the source product's separate page.
Making it one document instead is a small change now that the pagination is the
app's own: the two sheets would simply be laid out into one series of pages.

**3. The source's conduct page rates four things; the spec's data model names
one.** The PDF's "Συμπεριφορά και στάση" page has columns for *Συμμετοχή,
Αυτονομία, Διαγωγή* and *Συνέπεια*, plus the written overall result. The spec's
`GradeRow` names a single six-level conduct rating plus observations, and the
Excel registry has a single `Διαγωγή` column with exactly the six levels. M2
ships the spec's model — one rating, plus observations, plus the written result
— rather than inventing three more fields or silently dropping columns the
source has. If the other three are wanted they are three more coded columns on
the same row.

## PDF export: what was tried, and what works

This was M2's stated main risk, and it earned the billing. Recorded here because
M5 and M7 both build on it.

**AppKit's print pipeline does not work against this webview.**
`WKWebView.printOperationWithPrintInfo:` is the obvious route and the one most
sample code uses. Against wry's webview it returns a print view that is
**zero-sized and renders nothing**, so the job emits blank A4 pages for as long
as it is left running — the first attempt produced a **220MB file of empty
pages** before it was stopped. It was tried, on the dev Mac:

- with the print window hidden, and with it visible;
- with default print settings, and with paper size, orientation, margins,
  scaling and pagination modes all set explicitly;
- with the print view's frame forced to the paper's printable area (which the
  view does accept — it reports the new frame back);
- run both directly (`runOperation`) and modally for the window
  (`runOperationModalForWindow:`, so the run loop stays free).

All four produced the same empty pages. The PDF structure says why: every page
object is a correct A4 `MediaBox` with a content stream of 11 bytes.

**WebKit's other PDF path does work.** `createPDFWithConfiguration:` renders the
whole document, off-screen content included (verified against a document three
times taller than the window), and embeds the fonts it drew with. What it does
not do is paginate: given no rectangle it returns a single page as tall as the
content.

**So the app paginates.** The print window measures the rendered sheet and lays
it out into fixed A4 blocks — repeating the sheet header and the column headers
on each, and never cutting a row in half — and the macOS side captures one
rectangle per block, which PDFKit (the system's own framework, not a third-party
PDF writer) assembles into one file. On Windows, WebView2's
`ICoreWebView2_7::PrintToPdf` paginates the same blocks itself.

**This is still the spec's resolved approach** — the WebView print-to-PDF path,
not a native Rust PDF library — and it produces a real file in `exports/`. The
fallback in the spec's Resolved table (ship the gradebook, defer the PDF) was
**not needed**.

Two smaller traps worth keeping:

- **A hidden window runs no animation frames.** The print window originally
  waited on two `requestAnimationFrame` callbacks before reporting itself ready;
  hidden, they never came, and every export timed out. It waits on a timer and
  on `document.fonts.ready` instead — the font promise being the part that keeps
  Greek from being captured mid-fallback-font.
- **An element that is not in the document has no layout.** The paginator built
  its pages detached and measured them, so every height read as zero and a
  45-student roster came out as one clipped page. It attaches the pages before
  measuring, and the measurement is injected so the rule has unit tests that do
  not need a layout engine.

## What still needs a human

Unchanged from M1's finding, and stated plainly rather than claimed:

- **A genuine Explorer double-click, and therefore SmartScreen.** Everything
  above was launched programmatically — on Windows through a scheduled task in
  the console session, which is what gives the app an interactive desktop at
  all. `Start-Process` and a scheduled task both start a Mark-of-the-Web-tagged
  unsigned build without a prompt; only a real double-click is blocked. **Not
  performed.** It needs someone at the VM (or at the physical Windows PC) to
  double-click the installer and the exe from a synced folder.
- **Looking at the new screens.** Nobody has typed a grade into the packaged
  app's gradebook and looked at it. The M1 gate found a silent data-loss bug
  this way and by nothing else, so the M2 screens deserve the same five
  minutes: add a column, weight it, type marks, watch the average and the
  warning, and press both export buttons. **Not performed** — it needs a human
  at either Windows machine or at the Mac.

Worth knowing while doing it: an agent cannot click, which is why the print
self-test hook exists — it drives the *same* export path a button does, and it
is what produced the PDF evidence above.

## A note on the Google Drive carried risk

The spec carries an open risk that **Google Drive on Windows has never been
tested** — M0 skipped it and M1's run used a machine with no Drive client. The
VM has one, so M2 exercised it: the packaged exe ran from `G:\My Drive\…`,
created its data file and backup there, wrote a PDF into `exports/`, and left no
sidecars.

That is real evidence where there was none, but it is **not the whole of the
criterion** and the risk should stay recorded until:

- someone **double-clicks** the app from a Drive folder (this was a scheduled
  task), and
- the **online-only placeholder** case is driven against Drive, as M1 did
  against OneDrive. Drive streams files by a different mechanism, and that case
  is the leading suspect for what killed the previous attempt.

## Known gaps

- **Progress-check periods are not in M2**, per the product owner's decision of
  2026-09-20. The gradebook's `Περίοδος` is a caption on the printed sheet, not
  a period system.
- **Nothing else in the Βαθμοί module ships here.** The monthly attendance grid
  and the detailed absence-event log are M4's, per its scope line.
- **PDF layout fidelity has not been judged against the source pages.** The
  sheets follow the source's wording, header fields and column order, and come
  out as A4 with Greek rendering — but the side-by-side judgement against the
  source product's own pages is M9's acceptance criterion and a product-owner
  call.
