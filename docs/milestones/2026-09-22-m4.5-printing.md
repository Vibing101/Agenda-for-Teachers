# M4.5 — Printing attendance, behaviour and support

**Date:** 2026-09-22
**Branch:** `m4.5-printing`
**Signed off by:** <product owner, once reviewed>

Worked on **the dev Mac** (`uname -s` = `Darwin`, `VBoxManage list vms` lists
`MilestoneTesting`), with the Windows half of the gate driven over SSH into the
`MilestoneTesting` VM (`COMPUTERNAME` = `MILESTONETESTIN`, Windows 11 build
26200). Every result below says which machine produced it and whether an agent
or a human produced it. macOS 26.6.2, Node 24.15.0.

**M4.5 was not in the original roadmap.** It exists because M4 raised a real
conflict rather than resolving it silently: the spec promises PDFs for three of
M4's four surfaces in two places, while M4's own delivery-scope line named none.
The product owner's answer (2026-09-22) was that they are wanted, as their own
milestone. This is that milestone.

## What shipped

**Four printed sheets, each exporting a real PDF into `exports/`.**

- **The behaviour/incident register** (`Διαγωγή και περιστατικά`) — the source
  page's six columns, and **what prints is what the teacher is looking at**: the
  sheet carries the screen's current filter and names that filter in its own
  header.
- **The detailed absence register** (`Απουσίες και καθυστερήσεις`) — the
  source's `ΤΑΞΗ / ΜΑΘΗΜΑ / ΠΕΡΙΟΔΟΣ` header and its eight columns, with the two
  tick columns `Απ.` / `Καθ.` showing the stored `kind`, plus the source's two
  captioned boxes at the foot.
- **The cross-class support overview** (`Στήριξη και προσαρμογές`) — the source
  page's columns plus the screen's per-class support column, with each plan's
  **teacher-written status printed exactly as typed**.
- **The filled monthly attendance card** (`Απουσίες του μήνα`) — the roster
  against the days of the month, the source's four symbols, and the month's
  totals. **This is M4.5's own scope call; see "Decisions taken".**

**And two pieces of tidying that the work forced:**

- **`ExportButton` is now one shared component** (`src/components/`), not a copy
  per screen. M2's version, inside `GradesScreen`, called `todayIso()` itself —
  the one place in the codebase that still broke M3's rule that the shell is the
  only thing that reads the calendar. It now takes the day as a prop, and
  `GradesScreen` takes `today` from the shell like every other screen.
  `App.tsx`'s doc comment claimed this was already true; it is now.
- **The incident log's filter moved out of the screen** into
  `domain/behaviour.ts` as `filteredIncidents()`. The screen and the printed
  sheet call the same function, so they cannot disagree.

**No migration.** `user_version` stays at **5**. M4.5 adds no table, no column
and no stored field — these are print views over records M4 already holds, which
is what its scope line asked for.

## The two things M4.5 had to get right, and how they are held

**1. Nothing is recomputed for print.** Held by construction and then checked
the strong way round — not by asserting a number, but by asserting
*insensitivity*:

- `attendanceSheets.ts` builds the register from `eventsOfClass` and the card
  from `monthRows` / `monthTotals`. Neither function is in the other's call
  path.
- A test pushes 30 attendance marks into the planner and asserts the **register's
  whole document compares equal** to what it was. Another pushes 10 absence
  events and asserts the **card's whole document compares equal**. Either test
  fails the moment any future edit makes one sheet read the other's table at
  all.
- Both were confirmed to fail against deliberately broken code before being
  trusted: a mutation adding the event count into the card's totals, and one
  appending a mark count to the register's reason column, failed four tests
  between them.

**2. A plan's status is the teacher's sentence.** `supportSheet.ts` imports
neither `goalsOfPlan` nor `goalSummary` — there is no path from a goal to the
paper. A test rates **every** goal `met` and asserts the printed overview is
unchanged; a second deletes every goal and asserts the same; a third asserts no
goal text, no progress label and nothing matching `n/n` appears anywhere on the
sheet. A mutation that appended a met-goal count to the status failed two of
them.

The fixture is M4's own `supportFixture.ts`, unchanged, including the pair it
was built around: **Ελένη is `present` in the card on 05.11 and carries a logged
late arrival on 05.11 in the register.** Both sheets print their own version, and
a test asserts both at once from one screen.

## Open questions for the product owner

**1. Should the absence register's two per-event fields print as page-level
boxes, or as two more columns?** The source page has eight columns and two boxes
whose captions are exactly the names of two fields M4 stores *per event*. M4.5
prints them in the boxes, one attributed line per event. **It reads well for a
real register of a handful of lines and badly at volume**: a deliberate stress
fixture of 30 events produced a 30-line follow-up box that filled most of a
page. It was not clipped — all 30 lines are on the paper, verified — but it is
not what the source page looks like. The alternative is two more columns on an
already eight-column landscape sheet. One document builder changes it either
way; nothing stored moves.

**2. Should the incident register have a page-level notes field?** Its source
page carries a *ΠΡΟΣΘΕΤΕΣ ΣΗΜΕΙΩΣΕΙΣ* box and nothing in the data model
corresponds to it. M4.5 prints it blank, as ruled space to write in by hand,
because filling it would have needed a stored field and M4.5's scope line is
"no new data, no new fields, no schema change". If it should hold something
typed in the app, that is one column and one migration for whoever is told to
add it.

**3. The printed support overview has seven columns where the source has six.**
Deliberate, for the reason in "Decisions taken", and flagged so it is a recorded
call rather than a silent one.

### The PDFs, and what was actually verified about them

This is the milestone's whole point, so it is stated precisely.

**Real PDFs were produced on both operating systems by the packaged build**,
through the print self-test hook, which drives the *same* export path the button
does. Four sheets × two OSes = eight files, then read back with
`pdfinfo` / `pdffonts` / `pdftotext` on the Mac.

| | macOS (`createPDFWithConfiguration:`) | Windows (`PrintToPdf`) |
|---|---|---|
| Incident register | 1 page, `841 x 595 pts (A4)` | 1 page, `841.92 x 594.96 pts (A4)` |
| Absence register (31 events) | 4 pages | 4 pages |
| Month card (30 days) | 1 page | 1 page |
| Support overview | 1 page | 1 page |
| Fonts | embedded subsets, `HelveticaNeue` | embedded subsets, `Arial` CID/Identity-H |

**The page counts match on both platforms on all four sheets** — better than
M2's 45-row roster, which came out five pages on macOS and six on Windows.

**Greek renders, and it was checked rather than assumed.** Every sheet extracts
back as Greek with diacritics and final sigma intact on both OSes — `Διαγωγή και
περιστατικά`, `Τι συνέβη`, `Απουσίες του μήνα`, `Νοέμβριος 2026`,
`Δικαιολογημένη`, `Στήριξη και προσαρμογές`, `Ελένη Παπαδοπούλου`,
`Επιπλέον χρόνος στις γραπτές εργασίες` — not tofu, not question marks, not
Latin.

**What that does and does not establish.** It establishes that a real file is
produced, that it is A4, that its fonts are embedded, and that the Greek is in
it as Greek. It does **not** establish that the sheets *look right* — column
widths, whether a long `Τι συνέβη` wraps acceptably, whether a 31-line register
breaks across four pages sensibly. **Nobody has looked at one.** See "What still
needs a human", where this is the item that matters most for M4.5.

The stress fixture used for the evidence above is deliberately harsher than the
unit fixture: a three-line incident description and 31 absence events, so
wrapping and pagination were exercised rather than avoided.

## A testing hazard found at this gate, and it cost real time

**A stale build with the same bundle identifier silently shadows the one under
test, and a human double-click opens the wrong app.**

At this gate the product owner double-clicked the M4.5 build in the Drive test
folder and got a window showing `M0 — shell & persistence`, in English, reporting
`App folder: /Applications` and `Schema version 1`. Nothing was wrong with the
M4.5 build: its binary was byte-identical to the one built from the branch and
carried every current frontend asset. What happened is that **`/Applications`
held the M0 build from 2026-09-19, it was already running, and both bundles
declare the same `CFBundleIdentifier` (`gr.atzenta.teacher-planner`)** — so
LaunchServices activated the running instance instead of launching the copy that
was clicked.

Removing the `/Applications` copy did not fix it either, because by then
**LaunchServices held 30 registrations for that one identifier**, accumulated by
this project's own testing: every cloud test folder from M0 to M4.5, every
mounted `.dmg`, every build output, plus the copy now sitting in the Trash. Seven
still existed on disk; 23 pointed at things that were gone. The app was finally
run by invoking its binary directly, which bypasses LaunchServices altogether.

**Why no gate step could ever have caught this:** every automated step-5 launch
on macOS, at every milestone, used `open -a <full path>` or the binary path
directly. Those resolve the bundle themselves. Only a human double-click goes
through the identifier, and the human double-click is precisely the step that
has never been performed on macOS.

**Carry forward** (proposed for the standing brief):

1. **Before any manual pass, check the app's own `Schema version` line** against
   the milestone's `user_version`. It is the cheapest possible proof that the
   build in front of you is the build under test. `5` is M4.5; `1` was M0.
2. **Delete the previous milestone's test copies** rather than leaving them in
   place, and empty the Trash — a trashed bundle is still registered.
3. If a double-click opens the wrong build,
   `lsregister -dump | grep -c "Teacher Planner.app"` shows the damage, and
   `lsregister -kill -r -domain local -domain system -domain user` rebuilds it
   — at the cost of resetting the machine's "Open With" defaults.
